# Отчёт 3. Остаточные слабости после фикса (второй проход, НЕ исправлялись)

Второй, более глубокий проход уже по **исправленному** `service.py`. Цель — места, которые не
входили в основной список V1..V12: жизненный цикл аутентификации, изоляция арендаторов в LLM-тракте,
доступность и обработка ошибок, полномочия роли staff. Исходные дыры V1..V12 закрыты (см. Отчёт 2);
ниже — остаточные проблемы «глубины защиты». **Ничего из этого не исправлялось** по заданию.

Проверено на живом исправленном сервисе; доказательства — `evidence/extra/*.json`,
сводка `evidence/extra_summary.json`. Скрипт — `evidence/probe_extra.py`.

## Где искал (карта поверхности)

| Связь / место | Что проверял |
|---|---|
| клиент → /login | лимиты попыток, локаут, стойкость учётных данных |
| сессия (жизненный цикл) | истечение токена, logout, рост числа сессий/логов/отзывов |
| недоверенный ввод → prompt LLM | какие отзывы попадают в чей контекст (изоляция арендаторов) |
| решение staff → исполнитель | широта полномочий delete_tree, аудит разрушительных действий |
| валидация входа → обработка ошибок | ветки, дающие 500 вместо 400; утечки в теле ответа |
| /search → SQL LIKE | трактовка подстановочных символов |

## Найденные остаточные слабости

### N1. Нет лимита попыток и локаута на `/login` — перебор паролей (Medium, подтверждено)
- **Где:** ветка `POST /login` (service.py). Нет счётчика неудач, задержки, блокировки.
- **Проверка:** 6 неверных паролей подряд → все `401`, затем верный → `200`; аккаунт не блокируется.
  → `evidence/extra/N1_login_no_lockout.json`.
- **Почему плохо:** учебные пароли (`learn-*`) короткие; без лимита тривиален брутфорс/credential stuffing.
- **Комментарий к исправлению:** лимит попыток на аккаунт/IP, экспоненциальная задержка/локаут,
  по возможности хэширование паролей (сейчас хранятся открытым текстом — см. V12).

### N2. Жизненный цикл сессий: токены не истекают, нет logout, неограниченный рост (Low–Medium, рассуждение)
- **Где:** `self.sessions`, `self.reviews`, `self.logs` — растут без ограничений; токен валиден вечно.
- **Почему плохо:** украденный токен (напр. при XSS в чужом сценарии) действует бессрочно; бесконечное
  накопление сессий/логов/отзывов — медленное исчерпание памяти (доступность). Отзывы ещё и раздувают
  prompt помощника (стоимость/контекст).
- **Комментарий:** TTL и ревокация токенов, эндпоинт logout, ограничение числа/размера отзывов и логов,
  ротация журнала.

### N3. Пробелы валидации → `500` вместо `400` (Low, подтверждено; утечки НЕТ)
- **Где:** `str(x).lstrip("-").isdigit()` пропускает `--5` → `int("--5")` падает; тело-не-объект
  (`body.get` на списке) → `AttributeError`; `delete_tree` по несуществующему пути → `FileNotFoundError`.
- **Проверка:** `GET /profile?id=--5` → `500`; `GET /assistant/context?order_id=--1` → `500`;
  `POST /login` телом `[1,2,3]` → `500`; staff `delete_tree path='nope'` → `500`.
  → `N3a_profile_id_500`, `N3a2_context_orderid_500`, `N3b_nondict_body_500`, `N3c_delete_missing_500`.
- **Важно:** клиенту уходит только `{"error":"internal error"}`, трейс — лишь в stderr (фикс V12 держит).
  Это проблема устойчивости/доступности и «шумных» ошибок, а не утечки.
- **Комментарий:** строгая проверка целых (`str.isdigit` после единичного знака / `try int`),
  проверка `isinstance(body, dict)` на входе, 404/400 на отсутствующий путь.

### N4. Смешение отзывов арендаторов в контексте помощника (Medium, подтверждено)
- **Где:** `/assistant/context` подставляет в prompt **все** отзывы (любой автор, любой товар), а не
  относящиеся к заказу/клиенту.
- **Проверка:** alice оставляет отзыв `ALICE_INJECTED_MARKER_42`; bob запрашивает свой контекст
  `order_id=2` — маркер Alice присутствует в prompt Боба. → `N4_cross_user_reviews.json`.
- **Почему плохо:** несмотря на пометку «untrusted» (фикс V10), чужой пользовательский текст всё равно
  попадает в модельный контекст другого клиента — остаточная поверхность prompt injection и нарушение
  изоляции арендаторов: содержимое, управляемое атакующим, достигает сессии жертвы.
- **Комментарий:** включать в контекст только отзывы по товару этого заказа и/или умеренную выборку;
  изолировать недоверенные данные от инструкций на уровне формата, не только текстом-предупреждением.

### N5. Подстановочные символы LIKE в `/search` (Low, подтверждено)
- **Где:** `WHERE name LIKE ?` с `f"%{q}%"` без `ESCAPE` — `%` и `_` из `q` трактуются как шаблон.
- **Проверка:** `GET /search?q=_` (staff) возвращает совпадения по шаблону. → `N5_like_wildcard.json`.
- **Почему плохо (ограниченно):** это не SQL-инъекция (запрос параметризован). У staff и так полный
  доступ; у клиента выборка дополнительно скоупится по своему `id`, так что выгрузить чужое нельзя.
  Влияние — только управление логикой поиска.
- **Комментарий:** экранировать `%`/`_` и использовать `LIKE ? ESCAPE '\'`.

### N6. Роль staff: `delete_tree` сносит файлы другого клиента, нет аудита (Medium, подтверждено)
- **Где:** `/assistant/execute` → `delete_tree`: после фикса (V11) запрещены `.`/пустой/`..`, но
  `path='alice'` разрешён, т.е. staff удаляет каталог чужого клиента целиком; разрушительные действия
  нигде не логируются как события аудита.
- **Проверка:** staff `delete_tree path='alice'` → `200 {deleted: alice}`, после чего Alice не может
  прочитать свой чек (`404`). Восстанавливается рестартом. → `N6_staff_deletes_other_user.json`.
- **Почему плохо:** чрезмерные полномочия роли и отсутствие аудита — одна скомпрометированная
  staff-сессия (или ошибочное решение модели под staff) уничтожает данные клиентов без следа.
  Это сужение, но не устранение «excessive agency» из модели угроз.
- **Комментарий:** ограничить область `delete_tree` конкретным разрешённым подкаталогом, требовать
  явного подтверждения/причины, писать аудит-лог разрушительных операций, принцип наименьших привилегий.

### N8. Журнал хранит полные тела и решения помощника (Low, рассуждение)
- **Где:** в `self.logs` пишутся тела запросов (текст отзывов с полезной нагрузкой, решения
  `/assistant/execute`) и все заголовки, кроме замаскированных `X-Token`/`X-Role`.
- **Почему плохо:** журнал (доступен staff после фикса V8) накапливает потенциально вредоносный ввод и
  любые иные чувствительные заголовки, если появятся (напр. `Authorization`); долгое хранение без ротации.
- **Комментарий:** писать в журнал минимум полей, обобщать тела, белый список заголовков, ротация/лимит.

## Не является проблемой в этом стенде (зафиксировано, чтобы не искать повторно)
- CSRF неактуален: авторизация по заголовку `X-Token`, не по cookie.
- Отсутствие HTTPS приемлемо: процесс только на `127.0.0.1` (граница стенда).
- Mass assignment закрыт: `/orders` и `/reviews` читают только разрешённые поля, владелец/цена — с сервера.
- Гонки по БД не воспроизводятся: весь `dispatch` выполняется под `shop.lock`.
- Хранение паролей открытым текстом и вечные токены уже отмечены как долг в V12/N1–N2.

## Итог
Базовые уязвимости V1..V12 закрыты. Остаточные находки — это «глубина защиты»: стойкость
аутентификации (N1–N2), изоляция недоверенного ввода в LLM-тракте (N4), широта полномочий staff и
аудит (N6), устойчивость к некорректному вводу (N3, N5) и гигиена журналирования (N8). По заданию они
только задокументированы и не исправлялись.

## Принятые проектные решения (для защиты)

- **`delete_tree` не отключён полностью, а сведён к наименьшим привилегиям:** разрешён только в
  пределах собственного каталога пользователя и пишет аудит. Так сохраняется осмысленная функция
  «удалить свои данные», но исчезает возможность снести чужие файлы (устранение N6 и сужение
  «excessive agency» из модели угроз). Альтернатива — полный запрет инструмента — тоже допустима,
  если преподаватель предпочитает «deny by default».
- **Пароли:** перешли на PBKDF2-хэш в памяти процесса вместо хранения открытым текстом (закрывает
  часть долга из V12/N1). Учебные пароли `learn-*` продолжают работать, т.к. сверяется хэш.
- **Изоляция LLM-тракта (N4):** полностью изолировать арендаторов в общих отзывах нельзя (отзывы по
  товару публичны по смыслу), поэтому выбран скоуп «только отзывы этого товара + лимит + пометка
  untrusted» — остаточный риск задокументирован и признан приемлемым для стенда.
- **Доступность (N3):** некорректный ввод теперь даёт `400`, а не `500`; трейсы по-прежнему только в
  stderr сервера (фикс V12 сохранён).
