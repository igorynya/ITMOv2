# Сравнение спек логики: Spec Kit и OpenSpec

**Дата**: 2026-10-23

**Предмет сравнения**: две спеки одной фичи «фильтр подборок по тегу»,
подготовленные для команды логики.

**Артефакты**:

- Spec Kit: `practices/practice_05/spec_logic/spec.md`
- OpenSpec: `practices/practice_05/spec_logic_openspec/specs/collections-tag-filter/spec.md`
- Контекст OpenSpec: `practices/practice_05/spec_logic_openspec/proposal.md`
- Действующий контракт: `practices/practice_05/contract.md`
- Итоговая спека после ревью: `practices/practice_05/spec_review/spec.md`

## Краткий вывод

Обе спеки покрывают ядро фичи: фильтрацию только по активным подборкам,
один тег за запрос, регистронезависимое сравнение, пустой и неизвестный тег,
лимит длины, полный список `tags`, случайную выборку после фильтрации,
неизменность избранного и корзины.

Разница в первую очередь не в объёме покрытия, а в двух правилах:

1. **Неизвестный тег и `active_tag`** — прямое противоречие.
   Spec Kit требует эхо обрезанного запроса, OpenSpec — пустую строку.
2. **Теги длиннее 64 символов в `tags`** — OpenSpec исключает их, Spec Kit
   этого правила не содержит.

Также OpenSpec заметно короче и не описывает `500`, валидацию до обращения к
данным, общий формат ошибок, критерии успеха и сущности. Spec Kit ближе к
plan-ready спеке и лучше совпадает с текущим `contract.md` и кодом, но ему
не хватает явного правила про длинные теги в `tags` и нескольких границ,
которые уже зафиксированы в контракте.

**Рекомендация**: за основу реализации брать Spec Kit, добавив в него
исключение тегов длиннее 64 символов из `tags`; в OpenSpec исправить
`active_tag` для неизвестного тега на эхо и дополнить недостающие требования.

## 1. Структурное сравнение

| Параметр | Spec Kit | OpenSpec |
| --- | --- | --- |
| Формат | Полная feature-спека | Delta-спека `ADDED Requirements` |
| Нормативный язык | `MUST` / `MUST NOT` | `SHALL` / `SHALL NOT` |
| Пользовательские истории | 5 историй, P1–P2 | Отдельных историй нет, есть 12 требований |
| Требования | 42 FR в группах | 12 именованных требований |
| Сценарии | Given/When/Then в 5 историях | 35 сценариев `WHEN/THEN` |
| Критерии приёмки | AC-01–AC-18 | Отдельного блока нет, сценарии внутри требований |
| Критерии успеха | SC-001–SC-009 | Нет |
| Граничные случаи | Отдельный блок, 11 пунктов | Распределены по сценариям |
| Сущности | Есть `Key Entities` | Нет |
| HTTP-контракт | Есть предложенный контракт с примерами | Детального wire-контракта нет, только impact в proposal |
| Допущения | 17 пунктов | 5 открытых вопросов в proposal, не в спеке |
| Вне scope | Есть блок `Out of Scope` | Есть `Non-Goals` в proposal |
| Вопросы команде UI | 12 пунктов | Нет |

Структурно Spec Kit — это спека для планирования и реализации. OpenSpec —
компактная дельта для change-based workflow: она фиксирует, что добавляется,
но не претендует на полное описание контекста и нефункциональных границ.

## 3. Ключевые расхождения

### D1. `active_tag` для неизвестного тега — блокирующее

**Spec Kit**:

- FR-011: `active_tag` содержит каноническое написание при совпадении, эхо
  обрезанного запроса при отсутствии совпадения и пустую строку при
  отсутствии фильтра.
- Assumptions: для неизвестного тега выбран именно эхо, чтобы клиент мог
  показать введённое значение.
- `For the UI Team to Confirm` #1: это же правило вынесено на подтверждение.

**OpenSpec**:

- Строка 86: при неизвестном теге `active_tag` SHALL быть пустой строкой.
- Строка 91: сценарий подтверждает `active_tag` равен `""`.
- Строки 146–147: `active_tag` SHALL NOT быть произвольным эхом запроса.

**Влияние**: это не косметика. В текущем `contract.md` и коде неизвестный тег
возвращает обрезанный запрос, а UI использует непустой `active_tag`, которого
нет в `tags`, чтобы отличить устаревший тег от известного тега с пустым
результатом. Если принять OpenSpec-вариант, нужно менять контракт, UI-логику
автосброса и тесты API.

OpenSpec proposal сам фиксирует это как Open Question #1 и признаёт
расхождение с текущим кодом и `contract.md`; в спеке при этом уже выбран
вариант с пустой строкой.

**Рекомендация**: оставить эхо, как в Spec Kit, `contract.md` и реализации;
исправить OpenSpec-спеку. Если нужен пустой `active_tag`, это отдельное
решение с изменением контракта и UI.

### D2. Теги длиннее 64 символов в `tags` — существенное

**Spec Kit**: FR-015 запрещает дубли и пустые значения, FR-016 требует только
теги, которые есть у активной подборки. Явного исключения длинных тегов нет.
При буквальном чтении тег из 65 символов, лежащий в данных, попадёт в `tags`.

**OpenSpec**: строка 119 явно исключает значения длиннее 64 символов после
обрезки.

**Влияние**: расхождение в составе `tags` для данных с аномально длинными
тегами. Текущий `contract.md` и код уже исключают такие значения, поэтому
OpenSpec здесь точнее.

**Рекомендация**: добавить в Spec Kit явное требование исключать из `tags`
значения длиннее 64 символов Unicode после обрезки. Это не расширение фичи,
а фиксация уже принятого контракта.

### D3. Каноническое написание и порядок `tags` — низкое

Обе спеки требуют детерминированного выбора, но:

- Spec Kit в FR-010 не задаёт правило, а в Assumptions приводит пример
  «наименьшее по кодовым точкам»;
- OpenSpec в спеке ограничивается словом «детерминированный» (строка 120),
  а правило «лексикографически наименьшее» и сортировка по кодовым точкам
  остаются в proposal, не в самой спеке.

**Влияние**: реализация может выбрать разные детерминированные правила и
формально остаться в рамках обеих спек. Для приёмки лучше зафиксировать
правило нормативно.

**Рекомендация**: в обеих спеках указать: канонический вариант — наименьшая
последовательность кодовых точек Unicode после обрезки; `tags` сортируется по
возрастанию кодовых точек. Это совпадает с `contract.md` и текущим кодом.

### D4. Обработка ошибок — пробел OpenSpec

Spec Kit содержит:

- FR-024: валидация до обращения к данным, ошибка не содержит подборок;
- FR-025: машиночитаемое поле `error`;
- FR-026: внутренняя ошибка чтения — `500`, не маскируется под пустоту;
- примеры `400` и `500` в предложенном контракте.

OpenSpec описывает `400` для слишком длинного и повторного `tag`, но не
фиксирует валидацию до данных, общий формат ошибки и `500`.

**Влияние**: по OpenSpec-спеке можно реализовать обработку ошибок иначе, чем
требует действующий контракт, и формально пройти сценарии.

**Рекомендация**: перенести эти правила в OpenSpec-спеку или явно сослаться
на `contract.md`.

### D5. Полнота для реализации — Spec Kit

Spec Kit содержит `Key Entities`, `Success Criteria`, `Out of Scope`, вопросы
команде UI и предложенный HTTP-контракт. OpenSpec — это delta-спека: она
лаконичнее и лучше подходит для change-based workflow, но для планирования
реализации ей не хватает:

- критериев успеха;
- сущностей и границ данных;
- явного `500`;
- общего формата ошибок;
- требования «другие эндпоинты не меняются»;
- деталей избранного: счётчик, неактивные подборки;
- правила страницы: 12 — текущая конфигурация, а не жёсткая константа.

Это не делает OpenSpec-спеку неверной. Это разница назначения: OpenSpec
фиксирует дельту, Spec Kit — полную постановку.

## 4. Пробелы в обеих спеках

Оба документа не описывают явно:

- битый percent-encoding в `tag`;
- невалидный UTF-8 в `tag`;
- допустимость управляющих символов и NUL;
- точный текст ошибок (это нормально, если формат ошибки задан контрактом).

При этом `contract.md` и текущий код уже возвращают `400` для битого
percent-encoding и невалидного UTF-8, а управляющие символы и NUL не
запрещают. Если спеки должны быть источником истины, эти правила нужно
добавить хотя бы в одну из них и согласовать.

## 6. Что делать дальше

1. **Зафиксировать решение по D1.** Рекомендую эхо обрезанного запроса:
   это уже работает, описано в `contract.md` и нужно UI для автосброса.
2. **Исправить OpenSpec-спеку**:
   - `active_tag` для неизвестного тега — эхо, не пустая строка;
   - убрать или уточнить «SHALL NOT be arbitrary echo»;
   - добавить `500`, валидацию до данных и общий формат `error`;
   - добавить правило канонического выбора и сортировки `tags`;
   - при необходимости добавить критерии успеха и границы.
3. **Дополнить Spec Kit**:
   - исключение тегов длиннее 64 символов из `tags`;
   - явные правила для битого percent-encoding, невалидного UTF-8 и
     управляющих символов, если они входят в контракт.
4. **После правок** сравнить обе спеки повторно по этой же матрице. Ожидаемое
   состояние: D1 и D2 закрыты, D3 зафиксирован нормативно, D4 перенесён в
   OpenSpec, общие пробелы закрыты или явно вынесены в out of scope.

## 7. Итоговая оценка

- **Spec Kit**: полнее, лучше подходит как основа для плана и реализации;
  ближе к текущему контракту по `active_tag`, но требует явного правила про
  длинные теги и пару границ.
- **OpenSpec**: компактнее и точнее в правиле про длинные теги, но содержит
  блокирующее расхождение по `active_tag` и не покрывает обработку ошибок.
- **Для реализации**: Spec Kit + правка D2.
- **Для change-based workflow**: OpenSpec после исправления D1 и дополнения
  D4.
