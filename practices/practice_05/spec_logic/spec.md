# Feature Specification: Фильтр активных подборок по тегу (логика)

**Feature Branch**: N/A — спека лежит в `practices/practice_05/spec_logic`

**Created**: 2026-10-23

**Status**: Draft

**Input**: User description: "Опиши только серверное поведение фильтрации активных подборок по одному тегу: регистронезависимое сравнение и каноническое написание, пустой, неизвестный и слишком длинный тег, список доступных тегов, влияние на избранное и корзину, случайную выборку внутри фильтра и проверяемые критерии приёмки."

## Scope

Спека описывает только правила API, данных и выборки. Экран, чипы, состояния
интерфейса, доступность и вёрстка в эту спеку не входят и описаны в спеке UI.

Термины:

- **Активный пул** — все подборки, помеченные как активные (текущее поколение
  данных). Неактивные подборки прошлых поколений в фильтрации и в списке тегов
  не участвуют.
- **Тег подборки** — значение из `collection.tags`.
- **Доступные теги** — все теги активного пула без дублей и без пустых значений.
- **Запрошенный тег** — значение параметра `tag` после обрезки пробелов по краям.
- **Каноническое написание** — написание тега, взятое из активного пула, а не из
  запроса.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Отфильтровать активные подборки по одному тегу (Priority: P1)

Клиент запрашивает подборки с одним тегом и получает только активные подборки,
у которых есть этот тег. Без тега поведение остаётся прежним.

**Why this priority**: это основная ценность фичи; без фильтрации остальные
правила не имеют смысла.

**Independent Test**: запросить подборки без параметра, затем с существующим
тегом; сравнить состав и убедиться, что во втором ответе только подборки с этим
тегом, а лимит и случайность сохранены.

**Acceptance Scenarios**:

1. **Given** в активном пуле есть подборки с тегом «ужин», **When** клиент
   запрашивает подборки с этим тегом, **Then** ответ `200` содержит только
   активные подборки, у которых есть «ужин», и не более 12 штук.
2. **Given** параметр `tag` отсутствует, **When** клиент запрашивает подборки,
   **Then** возвращается случайная выборка всех активных подборок, как до фичи.
3. **Given** подборка имеет несколько тегов, **When** клиент фильтрует по любому
   из них, **Then** эта подборка попадает в результат.
4. **Given** подборка неактивна, **When** клиент фильтрует по её тегу, **Then**
   она не попадает в результат.
5. **Given** активная подборка не имеет тегов, **When** клиент фильтрует по
   любому непустому тегу, **Then** она не попадает в результат.

---

### User Story 2 - Регистронезависимое сравнение и каноническое написание (Priority: P1)

Запрос в любом регистре даёт один и тот же результат, а сервер сообщает
каноническое написание тега, чтобы клиент показывал одно значение.

**Why this priority**: без единого правила регистра один и тот же тег выглядел бы
как разные теги и давал разные результаты.

**Independent Test**: запросить «ужин», «УЖИН» и «Ужин» и сравнить наборы
подборок, список тегов и `active_tag`.

**Acceptance Scenarios**:

1. **Given** в пуле есть тег «ужин», **When** клиент запрашивает «УЖИН»,
   **Then** возвращается тот же набор подборок, что и для «ужин».
2. **Given** запрос совпал с тегом пула, **When** приходит ответ, **Then**
   `active_tag` равен каноническому написанию из пула, а не написанию запроса.
3. **Given** запрос « ужин » с пробелами по краям, **When** он обрабатывается,
   **Then** пробелы по краям отбрасываются, сравнение идёт по «ужин».
4. **Given** в пуле есть «Ужин» и «ужин», **When** сервер строит список тегов,
   **Then** в списке ровно одно значение, выбранное по детерминированному
   правилу, и фильтрация по любому регистру даёт один и тот же результат.

---

### User Story 3 - Понятная обработка пустого, неизвестного и слишком длинного тега (Priority: P1)

Клиент получает предсказуемый ответ на граничные значения параметра: пустой тег
не фильтрует, неизвестный даёт пустой список, слишком длинный отклоняется.

**Why this priority**: это защищает от ложных ошибок и от неограниченного ввода.

**Independent Test**: выполнить запросы с отсутствующим параметром, пустым
значением, пробелами, неизвестным тегом, 64 и 65 символами.

**Acceptance Scenarios**:

1. **Given** `tag` отсутствует, пуст или состоит только из пробелов, **When**
   клиент запрашивает подборки, **Then** фильтр не применяется, `active_tag`
   равен пустой строке.
2. **Given** тег отсутствует в активном пуле, **When** клиент фильтрует по нему,
   **Then** ответ `200`, `collections` — пустой массив, остальные поля сохранены;
   это не ошибка.
3. **Given** запрошенный тег длиннее 64 символов, **When** клиент фильтрует,
   **Then** ответ `400` с ошибкой, подборки не возвращаются.
4. **Given** запрошенный тег ровно 64 символа, **When** клиент фильтрует,
   **Then** запрос обрабатывается как обычный тег.
5. **Given** параметр `tag` передан несколько раз, **When** клиент фильтрует,
   **Then** ответ `400` с ошибкой, потому что за запрос допускается один тег.

---

### User Story 4 - Случайная выборка внутри отфильтрованного набора (Priority: P2)

При фильтрации сервер применяет лимит и случайность к уже отфильтрованному
набору, а не к полному пулу.

**Why this priority**: иначе фильтр мог бы возвращать пустой результат при
наличии подходящих подборок.

**Independent Test**: создать больше 12 подборок с одним тегом и меньше 12 с
другим; проверить размер и состав выборок.

**Acceptance Scenarios**:

1. **Given** по тегу больше 12 активных подборок, **When** клиент фильтрует,
   **Then** он получает 12 случайных подборок этого тега без повторов.
2. **Given** по тегу меньше 12 подборок, **When** клиент фильтрует, **Then** он
   получает все подходящие подборки, без добора из других тегов.
3. **Given** по тегу нет подборок, **When** клиент фильтрует, **Then** он
   получает `collections: []`, а не ошибку и не 12 случайных подборок.
4. **Given** один и тот же запрос повторён, **When** пул не менялся, **Then**
   набор может отличаться по составу и порядку, но всегда остаётся внутри
   выбранного тега.

---

### User Story 5 - Избранное и корзина не зависят от фильтра (Priority: P1)

Фильтрация не меняет избранное, его список и ссылки на корзину. Избранное и
корзина работают как до фичи при активном фильтре и без него.

**Why this priority**: это существующая пользовательская ценность, которую нельзя
ломать ради фильтра.

**Independent Test**: добавить подборку в избранное, запросить фильтр, проверить
`favorites` и `/api/favorites`, затем открыть корзину отфильтрованной карточки.

**Acceptance Scenarios**:

1. **Given** у посетителя есть избранное, **When** он запрашивает подборки с
   фильтром, **Then** `favorites` содержит те же идентификаторы, что и без
   фильтра.
2. **Given** избранная подборка не совпадает с фильтром, **When** клиент
   фильтрует, **Then** она остаётся в избранном и отсутствует только в
   отфильтрованном `collections`.
3. **Given** активный фильтр, **When** клиент добавляет или удаляет избранное,
   **Then** операция выполняется как раньше и не зависит от фильтра.
4. **Given** подборка видна под фильтром, **When** клиент запрашивает ссылку на
   корзину, **Then** ссылка создаётся или берётся из кэша как раньше.
5. **Given** активный фильтр, **When** клиент открывает список избранного,
   **Then** список не фильтруется и не меняется.

---

### Edge Cases

- В активном пуле нет ни одной подборки: `collections: []`, `tags: []`,
  `active_tag` — пустая строка или эхо запроса по правилам ниже.
- У подборки `tags` пустой массив: она не совпадает ни с одним непустым тегом.
- В одной подборке тег повторяется или отличается регистром: подборка всё равно
  совпадает, а в списке тегов дубля нет.
- Тег в данных пустой или состоит из пробелов: в список доступных тегов не
  попадает и ни с чем не совпадает.
- Запрошенный тег состоит только из пробелов: считается пустым, фильтр не
  применяется.
- В запросе несколько параметров `tag`: `400`, даже если значения совпадают.
- Значение тега содержит кириллицу и URL-кодирование: сервер сравнивает
  раскодированное значение.
- Длина тега измеряется в символах Unicode, а не в байтах: 64 кириллических
  символа допустимы, 65 — нет.
- Поколение данных сменилось между запросами: каждый ответ внутренне
  согласован — список тегов и отфильтрованные подборки относятся к одному
  активному пулу.
- Подходящих подборок 0, 1 или 11: возвращается ровно столько, сколько есть.
- Избранная подборка стала неактивной: её поведение в избранном не меняется этой
  фичей.

## Requirements *(mandatory)*

### Functional Requirements

**Фильтрация**

- **FR-001**: Система MUST фильтровать только по активным подборкам текущего
  поколения; неактивные подборки MUST NOT попадать в `collections`.
- **FR-002**: Подборка MUST считаться подходящей, если хотя бы один её тег
  совпадает с запрошенным без учёта регистра после обрезки пробелов по краям.
- **FR-003**: Фильтр MUST поддерживать ровно один тег за запрос; несколько
  значений `tag` MUST приводить к `400`.
- **FR-004**: Отсутствующий, пустой или состоящий только из пробелов `tag` MUST
  означать отсутствие фильтра.
- **FR-005**: При отсутствии фильтра система MUST возвращать случайную выборку
  всех активных подборок в прежнем объёме и формате.
- **FR-006**: Фильтр MUST NOT менять состав данных, схему хранения, структуру
  подборки или существующие поля ответа.

**Сравнение и каноническое написание**

- **FR-007**: Сравнение тегов MUST быть регистронезависимым для Unicode, без
  зависимости от локали, транслитерации, удаления диакритики и стемминга.
- **FR-008**: Пробелы по краям запрошенного тега MUST отбрасываться; пробелы
  внутри значения MUST сохраняться как значимые.
- **FR-009**: Каноническое написание MUST браться из активного пула, а не из
  запроса.
- **FR-010**: Если в пуле есть несколько написаний одного тега, отличающихся
  только регистром, система MUST выбрать одно детерминированное каноническое
  написание и использовать его и в `tags`, и в `active_tag`.
- **FR-011**: `active_tag` MUST содержать каноническое написание при совпадении с
  пулом, эхо обрезанного запроса при отсутствии совпадения и пустую строку при
  отсутствии фильтра.
- **FR-012**: `active_tag` MUST NOT содержать необрезанные пробелы по краям.

**Список доступных тегов**

- **FR-013**: Ответ MUST содержать `tags` — все доступные теги активного пула,
  независимо от текущего фильтра.
- **FR-014**: `tags` MUST NOT сужаться до тегов отфильтрованного результата.
- **FR-015**: `tags` MUST NOT содержать дубли, пустые значения и значения из
  пробелов.
- **FR-016**: `tags` MUST содержать только теги, которые есть хотя бы у одной
  активной подборки; тегов без подборок в списке нет.
- **FR-017**: `tags` MUST быть детерминированно упорядочен для одного и того же
  набора данных; порядок задаёт сервер.
- **FR-018**: Порядок `tags` MUST NOT зависеть от случайной выборки подборок.
- **FR-019**: `tags` MUST присутствовать в каждом успешном ответе, в том числе
  без фильтра и при пустом результате; при отсутствии тегов это пустой массив.

**Границы значения и ошибки**

- **FR-020**: Запрошенный тег длиннее 64 символов Unicode после обрезки MUST
  отклоняться с `400` и понятной ошибкой.
- **FR-021**: Запрошенный тег длиной ровно 64 символа MUST приниматься.
- **FR-022**: Неизвестный тег MUST давать `200` с `collections: []`; это MUST NOT
  быть `404` или `400`.
- **FR-023**: При неизвестном теге `tags` и `favorites` MUST оставаться полными,
  а `active_tag` MUST следовать правилу FR-011.
- **FR-024**: Ошибка валидации MUST возвращаться до обращения к данным и MUST NOT
  содержать подборок.
- **FR-025**: Ошибка валидации MUST содержать машиночитаемое поле `error` с
  понятным текстом; формат ошибки — часть предлагаемого контракта.
- **FR-026**: Внутренняя ошибка чтения данных MUST оставаться `500` и не
  маскироваться под пустой результат.

**Случайная выборка**

- **FR-027**: Случайная выборка MUST применяться внутри отфильтрованного набора,
  а не до фильтрации.
- **FR-028**: Ответ MUST содержать не более 12 подборок (текущий размер
  страницы); при меньшем числе подходящих — все.
- **FR-029**: При нуле подходящих подборок MUST возвращаться пустой массив, без
  добора из других тегов и без ошибки.
- **FR-030**: Повторный одинаковый запрос MUST NOT гарантировать тот же состав
  или порядок, но MUST оставаться внутри выбранного тега.
- **FR-031**: Внутри одной выборки подборки MUST NOT повторяться.
- **FR-032**: Список `tags` и отфильтрованные подборки в одном ответе MUST быть
  согласованы и относиться к одному активному пулу.

**Избранное и корзина**

- **FR-033**: `favorites` в ответе MUST содержать полный список идентификаторов
  избранного посетителя независимо от фильтра и MUST NOT сужаться фильтром.
- **FR-034**: Список избранного, добавление и удаление избранного MUST работать
  без изменений при активном фильтре.
- **FR-035**: Фильтр MUST NOT менять состав избранного, счётчик избранного и
  поведение избранного для неактивных подборок.
- **FR-036**: Создание и кэширование ссылки на корзину MUST работать без
  изменений для любой подборки, видимой под фильтром.
- **FR-037**: Фильтр MUST NOT влиять на срок жизни кэша корзины и на признаки
  `cart_url` в ответе.

**Совместимость и границы**

- **FR-038**: Успешный ответ MUST сохранять существующие поля подборки и
  `favorites` и MUST добавлять только `tags` и `active_tag`.
- **FR-039**: `collections`, `tags` и `favorites` MUST быть массивами, а не
  `null`, в том числе при пустом результате.
- **FR-040**: Схема БД MUST NOT меняться; теги MUST по-прежнему читаться из
  существующего хранения.
- **FR-041**: Фича MUST NOT добавлять несколько тегов, поиск по тексту,
  сортировку, счётчики и сохранение фильтра на сервере.
- **FR-042**: Существующий формат ошибок и коды для остальных эндпоинтов MUST NOT
  меняться.

### Key Entities

- **Подборка**: активная запись текущего поколения с идентификатором, набором
  тегов, содержимым и признаком активности. В фильтрации участвует только
  активная подборка; её теги — единственный источник совпадений.
- **Тег**: значение из набора тегов подборки. Один тег может входить в несколько
  подборок; группа написаний, различающихся только регистром, представляет один
  тег с одним каноническим написанием.
- **Набор доступных тегов**: производное от активного пула множество
  канонических тегов без дублей и пустых значений. Не хранится отдельно и не
  зависит от текущего фильтра.
- **Избранное посетителя**: связь посетителя с подборками, не зависящая от
  фильтра, активности подборки и текущей выборки.
- **Кэш ссылки на корзину**: сохранённая ссылка подборки со сроком жизни, не
  зависящая от фильтра.

## Proposed HTTP Contract (на согласование)

Статус: предложение команды логики. Точные имена полей и порядок тегов
подлежат согласованию с командой UI. Поведение ниже обязательно для приёмки,
если согласование не изменит контракт.

Запрос:

```http
GET /api/collections?tag=ужин
Accept: application/json
```

Успех `200`:

```json
{
  "collections": [
    {
      "id": "dinner-500-1792666479",
      "title": "Ужин на двоих",
      "tags": ["ужин", "бюджет"],
      "items": [],
      "total": 0
    }
  ],
  "favorites": ["friends-lunch-1792666479"],
  "tags": ["завтрак", "перекус", "ужин"],
  "active_tag": "ужин"
}
```

- Поля подборки — существующие, без переименований.
- `tags` — полный список доступных тегов активного пула.
- `active_tag` — каноническое значение, эхо запроса для неизвестного тега или
  пустая строка.

Ошибка валидации `400`:

```json
{ "error": "tag is too long" }
```

Другие ошибки валидации используют то же поле `error`, например
`{ "error": "tag must be specified once" }`.

Внутренняя ошибка `500`:

```json
{ "error": "cannot load collections" }
```

## Acceptance Criteria

- **AC-01**: Запрос без `tag` возвращает не более 12 случайных активных
  подборок, `active_tag: ""` и полный `tags`.
- **AC-02**: Запрос с существующим тегом возвращает только активные подборки,
  содержащие этот тег.
- **AC-03**: Наборы для «ужин», «УЖИН», «Ужин» и « ужин » совпадают по составу;
  `active_tag` во всех случаях — одно каноническое написание.
- **AC-04**: `active_tag` никогда не содержит пробелов по краям.
- **AC-05**: `tags` содержит все и только теги активного пула, без дублей и
  пустых значений, в стабильном порядке.
- **AC-06**: `tags` не сужается при активном фильтре и не зависит от случайной
  выборки.
- **AC-07**: Неизвестный тег даёт `200`, `collections: []`, полные `tags` и
  `favorites`, без ошибки.
- **AC-08**: Тег длиной 65 символов Unicode даёт `400` с полем `error` и без
  подборок.
- **AC-09**: Тег длиной 64 символа обрабатывается как обычный тег.
- **AC-10**: Значение из одних пробелов не фильтрует и даёт `active_tag: ""`.
- **AC-11**: Повторённый параметр `tag` даёт `400`.
- **AC-12**: При 13 и более подходящих подборках возвращается ровно 12 без
  повторов; при 11 — ровно 11; при 0 — пустой массив.
- **AC-13**: В отфильтрованном ответе нет подборок без запрошенного тега и нет
  подборок из неактивного поколения.
- **AC-14**: `favorites` в ответе с фильтром совпадает с `favorites` без фильтра
  для того же посетителя.
- **AC-15**: Добавление и удаление избранного, а также список избранного
  работают под фильтром как раньше.
- **AC-16**: Ссылка на корзину для видимой под фильтром подборки создаётся и
  переиспользуется из кэша как раньше.
- **AC-17**: В успешном ответе присутствуют все прежние поля, а `collections`,
  `tags`, `favorites` — массивы даже при пустоте.
- **AC-18**: Ответы с фильтром и без него не меняют схему БД и другие
  эндпоинты.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% запросов с отсутствующим или пустым тегом дают прежнее
  поведение и полный список тегов.
- **SC-002**: Все варианты регистра одного тега дают один и тот же набор
  подборок и одно и то же значение `active_tag`.
- **SC-003**: Ни один успешный ответ не содержит больше 12 подборок и ни один
  отфильтрованный ответ не содержит подборок без выбранного тега.
- **SC-004**: При 12 и более подходящих подборках возвращается 12; при меньшем
  числе — ровно столько, сколько есть; при нуле — пустой массив.
- **SC-005**: Неизвестный тег всегда даёт `200`, а тег длиннее 64 символов —
  `400`; других кодов для этих случаев нет.
- **SC-006**: `favorites` и операции избранного не отличаются при включённом и
  выключенном фильтре.
- **SC-007**: Список тегов детерминирован для одного набора данных и не зависит
  от случайной выборки.
- **SC-008**: Схема БД и существующий формат ответа не меняются; добавлены
  только `tags` и `active_tag`.
- **SC-009**: Для одного ответа список тегов и подборки относятся к одному
  активному пулу.

## Assumptions

- Один тег на запрос; несколько параметров `tag` считаются ошибкой `400`.
- Схема БД не меняется; теги читаются из существующего хранения.
- Если подходящих подборок меньше 12, возвращаются все.
- Лимит 12 — текущий размер страницы; при другой конфигурации правило «не более
  размера страницы» сохраняется.
- Пустой, отсутствующий или пробельный `tag` означает отсутствие фильтра;
  пробелы по краям отбрасываются, внутренние пробелы значимы.
- Регистронезависимость трактуется как Unicode case folding без локали и без
  эвристик; транслитерация, синонимы и стемминг не поддерживаются.
- При нескольких написаниях одного тега каноническим считается детерминированно
  выбранное написание (например, наименьшее в порядке кодовых точек); конкретное
  правило фиксируется при реализации и не должно меняться между запросами.
- Для неизвестного тега `active_tag` по умолчанию равен обрезанному запросу как
  эху, потому что канонического написания в пуле нет. Это выбрано, чтобы клиент
  мог показать введённое значение; требуется подтверждение команды UI.
- Теги в данных считаются уже нормализованными: без пробелов по краям и без
  пустых значений; такие значения в список не попадают независимо от данных.
- Список тегов сортируется сервером детерминированно; клиент не сортирует его
  самостоятельно.
- Активный пул — текущее поколение; смена поколения между запросами допустима,
  но каждый ответ внутренне согласован.
- Избранное и корзина существуют и работают; фича не меняет их правила, включая
  поведение избранного для неактивных подборок.
- Внутренние ошибки чтения данных остаются `500`; пустой результат ими не
  является.

## Out of Scope

- Экран, чипы, состояния загрузки, пустоты и ошибки, доступность, вёрстка.
- Выбор нескольких тегов, поиск по тексту, сортировка, счётчики подборок.
- Сохранение фильтра в URL или на сервере.
- Изменение схемы БД, формата хранения тегов, логики избранного и корзины.
- Новые эндпоинты, кроме обсуждения списка тегов в существующем ответе.
- Изменение кодов и сообщений ошибок других эндпоинтов.

## For the UI Team to Confirm

1. `active_tag` для неизвестного тега: эхо обрезанного запроса (текущее
   предположение) или пустая строка; как UI показывает название тега в пустом
   результате.
2. `tags` и `active_tag` присутствуют в каждом успешном ответе, включая запрос
   без фильтра и пустой результат; при `400` возвращается только `error`.
3. `tags` содержит все теги активного пула, а не только совпавшие; поэтому
   выбранный тег не исчезает из списка после фильтрации.
4. Тегов без подборок в `tags` нет; любой тег вне списка даёт пустой результат
   `200`, а не ошибку.
5. Порядок `tags` задаёт сервер, он детерминирован и не зависит от случайной
   выборки; UI не сортирует и не дедуплицирует теги сам.
6. Регистр нормализует только сервер: UI отправляет выбранное значение как есть,
   а активным считает чип по `active_tag`.
7. `favorites` в ответе всегда полный и не зависит от фильтра; счётчик
   избранного не меняется.
8. Список избранного (`/api/favorites`) не фильтруется; фильтр к нему не
   применяется.
9. Повторный параметр `tag` даёт `400`; UI отправляет не более одного значения.
10. «Ещё подборки» при активном фильтре повторяет запрос с тем же тегом и
    получает новую случайную выборку внутри него.
11. Ограничение 64 символа считается в символах Unicode после обрезки пробелов;
    UI не должен генерировать более длинные значения.
12. Избранное и корзина не зависят от фильтра и работают при активном фильтре и
    при возврате без него.
