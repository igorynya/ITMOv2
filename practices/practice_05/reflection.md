# Reflection: согласование вопросов по фильтру подборок

**Дата**: 2026-10-23

**Контекст**: ревью двух частичных спек — UI (`spec_ui/spec.md`) и логики
(`spec_logic/spec.md`). Три расхождения меняли поведение фичи, поэтому были
вынесены на согласование, а не решены молча.

## Вопрос 1. Что делать с выбранным тегом при возврате с «Избранного»

**Почему возник**: UI-спека предполагала сохранение и восстановление тега, а
спека логики этот сценарий не описывала. Бриф отдельно просил согласовать
поведение при возврате.

**Варианты**:

1. Сохранять тег и восстанавливать его при возврате на «Все», загружая
   подборки с фильтром.
2. Сбрасывать фильтр при переходе на «Избранное» и показывать все подборки.
3. Сохранять только выделение чипа, но не перезагружать данные до действия
   пользователя.

**Решение**: сохранять и восстанавливать тег при возврате; подборки
загружаются заново с этим фильтром.

**Следствия**: на «Избранном» фильтр не применяется и чипы скрыты, но выбор
живёт в памяти вкладки «Все». При возврате выполняется отдельный запрос.
Зафиксировано в `contract.md` и FR-045 итоговой спеки.

## Вопрос 2. Как показывать тег, которого больше нет в актуальном списке

**Почему возник**: UI-спека требовала автосброс с уведомлением, но также
описывала пустое состояние с названием тега. Спека логики для неизвестного
тега возвращает `200`, пустой `collections` и эхо запроса в `active_tag`, не
давая отдельного сигнала об исчезновении.

**Варианты**:

1. Автоматически сбрасывать фильтр на «Все», перезагружать подборки и
   показывать короткое уведомление.
2. Показывать пустое состояние с названием исчезнувшего тега и кнопкой
   сброса.
3. Оставлять фильтр активным и пустой результат до ручного сброса.

**Решение**: автосброс на «Все» с уведомлением. UI сравнивает `active_tag`
со списком `tags` без учёта регистра; при отсутствии совпадения считает тег
устаревшим.

**Следствия**: уведомление должно быть видимым и объявляться через живой
регион. Текст «Тег больше недоступен, фильтр сброшен», показ около 5 секунд,
без модального окна. Зафиксировано в `contract.md` и FR-034 итоговой спеки.

## Вопрос 3. Что делать с тегом длиннее 64 символов в данных

**Почему возник**: API отклоняет запрос с тегом длиннее 64 символов с `400`,
а UI строит чипы из списка `tags`. Если такое значение попадёт в список,
пользователь увидит чип, который нельзя выбрать.

**Варианты**:

1. Не включать такие значения в `tags`; UI физически не может выбрать
   недопустимый тег.
2. Показывать тег в `tags` и обрабатывать `400` отдельным сообщением с
   предложением сброса.
3. Обрезать тег до 64 символов, меняя данные и рискуя склеить разные теги.

**Решение**: не включать значения длиннее 64 символов Unicode после обрезки
в `tags`. Ограничение `400` остаётся для прямых клиентов API.

**Следствия**: подборка с таким тегом остаётся в выдаче «Все», но сам тег не
доступен как фильтр. UI не добавляет собственную проверку длины.
Зафиксировано в `contract.md` и FR-014 итоговой спеки.

## Дополнительное согласование

После вопросов отдельно согласовано, что все предложения по умолчанию из
`spec_review/gaps.md` принимаются как fallback: если при планировании или
реализации не принято иное, применяются они, а отклонение фиксируется в
`contract.md` и `spec.md`.

При этом `GAP-01` (каноническое написание), `GAP-02` (порядок `tags`),
`GAP-05` (уведомление об исчезнувшем теге), `GAP-09` (граница размера
страницы) и `GAP-10` (нормализация тегов из данных) перенесены в требования
и допущения итоговой спеки. `GAP-03`, `GAP-04`, `GAP-06`, `GAP-07` и
`GAP-08` остаются реализационными defaults.
