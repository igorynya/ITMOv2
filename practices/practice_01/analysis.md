# Анализ процесса: AS IS и TO BE

## AS IS

Событие: внешний клиент (CI/разработчик) отправляет HTTP POST на `/api/reviews` с JSON телом.

Участники и поток данных:
- Клиент → FastAPI эндпоинт `create_review(payload: dict)` [TRAINING_PR.diff: app/api.py, строки 35–38].
- Эндпоинт вызывает `review_service.review(payload["diff"])` без проверки наличия ключа [35–38].
- `ReviewService.review` формирует промпт и вызывает `llm.generate(prompt)` [app/review_service.py, строки 19–22].
- Возврат словаря `{"comment": answer}` клиенту [строка 22].

Точки риска и задержки:
- Отсутствие валидации входа → `KeyError` и 500 при отсутствии `diff`.
- Нет обработки исключений из LLM → неконтролируемые 5xx.
- Diff попадает в промпт без ограничений → риск prompt injection и больших задержек/стоимости.


## TO BE

Небольшие изменения для контроля качества и стабильности:
1. Валидация тела запроса (наличие и тип `diff: str`).
2. Ограничение размера и нормализация `diff` (усечение/ошибка при превышении лимита).
3. Обработка исключений LLM с маппингом на HTTP‑коды.

```mermaid
flowchart LR
    A[POST /api/reviews] --> B[Валидация тела]
    B -- ok --> C[Подготовка промпта]
    C --> D[Вызов llm.generate]
    D -- ok --> E[Ответ {comment}]
    B -- bad --> X[422/400]
    D -- exception --> Y[502/503 + лог]
```

## Разница

| Что меняется | AS IS | TO BE | Как проверим изменение |
|---|---|---|---|
| Валидация входа | Нет проверки `payload["diff"]` | Схема/проверка типа и наличия | Запрос без `diff` → 422/400 |
| Обработка ошибок LLM | Исключения пробрасываются | try/except с маппингом | Смоделировать исключение → 502/503 |
| Контроль размера diff | Нет | Ограничение/усечение | Тело > лимита → предсказуемый ответ |

## Как использовали AI

- Для чего: структурировать AS IS/TO BE по `TRAINING_PR.diff`.
- Тип промпта: structured summary.
- Строка в [`prompts.md`](prompts.md): P1-01, P1-02.
- Что проверили и исправили сами: сопоставили утверждения с конкретными строками diff и ограничили вывод только фактами из diff.
