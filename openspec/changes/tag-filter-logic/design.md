# Design: фильтр подборок по тегу (логика)

## Context

Целевой сервис — `practices/practice_04/collections`: Go, `net/http`, SQLite,
существующий эндпоинт `GET /api/collections` уже отдаёт `collections`,
`favorites` и (в текущем коде) `tags`/`active_tag`. Подборки хранятся в таблице
`collections`, теги — JSON-массив в колонке `tags`; отдельной таблицы тегов нет.
Активный пул читается одним запросом `ActivePool`. Избранное и кэш корзины
хранятся отдельно и от фильтра не зависят. Мотивация — в `proposal.md`.

Текущий код уже содержит разбор `tag`, проверку длины, регистронезависимое
сравнение и фильтрацию. Расхождение: для неизвестного тега `active_tag`
сейчас отдаёт эхо обрезанного запроса, а задание требует каноническое значение
или пустую строку. Это вынесено в открытые вопросы.

## Goals / Non-Goals

**Goals:**

- Описать и реализовать фильтрацию активного пула по одному тегу без изменения
  схемы БД и без нового эндпоинта.
- Сохранить текущий формат ответа и добавить только `tags` и `active_tag`.
- Применить лимит и случайную выборку после фильтрации.
- Не затронуть избранное, корзину и другие эндпоинты.

**Non-Goals:**

- UI, чипы, состояния экрана, доступность.
- Мультивыбор тегов, поиск, сортировка, счётчики.
- SQL-фильтрация по тегам или новая таблица/индекс под теги.
- Изменение схемы БД, генератора подборок и логики корзины.

## Decisions

### 1. Фильтрация в HTTP-слое поверх активного пула

`ActivePool` остаётся единственным источником и `tags`, и `collections`.
Фильтрация выполняется в памяти после загрузки пула.

- Почему: теги лежат JSON-массивом, а пул небольшой; это сохраняет схему БД и
  гарантирует, что `tags` и `collections` в одном ответе относятся к одному
  поколению.
- Альтернатива: SQL `LIKE`/`json_each` — потребовал бы индексов и усложнил
  регистронезависимость для Unicode. Отклонено.

### 2. Один необязательный параметр `tag`

`tag` читается из query один раз. Отсутствие, пустая строка или строка из
пробелов означают отсутствие фильтра. Более одного значения `tag` — `400`.
Валидация длины и UTF-8 выполняется до чтения активного пула.

- Почему: контракт задания допускает ровно один тег; ранняя валидация не
  маскирует ошибку ввода под пустой результат.
- Альтернатива: брать первое значение и игнорировать остальные — неявно
  меняет смысл запроса. Отклонено.

### 3. Регистронезависимое сравнение через Unicode simple case folding

Сравнение тегов выполняется без учёта регистра средствами стандартной
библиотеки Go для Unicode, без локали, транслитерации и стемминга. Пробелы по
краям отбрасываются, внутренние пробелы значимы.

- Почему: это предсказуемо для кириллицы и не требует новых зависимостей.
- Альтернатива: `strings.ToLower` с локалью — зависит от локали и даёт
  нестабильный результат. Отклонено.

### 4. Каноническое написание из пула

Список доступных тегов строится из активного пула: значения обрезаются,
пустые и слишком длинные отбрасываются, дубли без учёта регистра
объединяются. Каноническим считается детерминированно выбранное написание
(по умолчанию — лексикографически наименьшее после обрезки). `active_tag`
берётся из этого списка.

- Почему: клиент получает одно значение на тег и не зависит от регистра
  запроса.
- Альтернатива: каноническим считать написание запроса — тогда `tags` и
  `active_tag` расходились бы. Отклонено.

### 5. Случайная выборка после фильтрации

Сначала отбираются подборки с тегом (или весь пул без фильтра), затем
перемешиваются и обрезаются до размера страницы (по умолчанию 12). Если
подходящих меньше лимита, возвращаются все; при нуле — пустой массив.

- Почему: иначе фильтр мог бы вернуть пусто при наличии подходящих подборок.
- Альтернатива: перемешивать весь пул и фильтровать после — теряет подборки
  и нарушает лимит. Отклонено.

### 6. Совместимость избранного, корзины и БД

`favorites` читается отдельно и не фильтруется. `/api/favorites`, добавление
и удаление избранного, создание ссылки на корзину не меняются. Схема БД и
формат хранения тегов остаются прежними; новых зависимостей нет.

- Почему: это существующая пользовательская ценность и граница фичи.
- Альтернатива: фильтровать избранное тем же тегом — противоречит требованию
  «избранное не меняется». Отклонено.

## Risks / Trade-offs

- **Расхождение по `active_tag` для неизвестного тега** (пустая строка против
  текущего эха) → зафиксировать решение до реализации; до этого тест должен
  явно закреплять выбранное поведение.
- **Регистронезависимость Unicode не покрывает все языковые тонкости** (simple
  case folding не равен полному case folding) → считать это границей фичи и
  покрыть тестами кириллицу и Latin.
- **Случайная выборка делает тесты нестабильными** → проверять размер, состав
  и отсутствие дублей, а не конкретный порядок.
- **Фильтрация в памяти при росте пула** → пул ограничен текущим поколением;
  при необходимости позже можно добавить SQL-фильтрацию без изменения
  контракта.
- **Несколько написаний тега в пуле** → детерминированное правило должно быть
  одинаковым для `tags`, `active_tag` и фильтрации; закрепить тестом.

## Migration Plan

Изменение обратно совместимо: новых колонок и миграций нет. При откате
достаточно вернуть прежний обработчик; данные не затрагиваются. Порядок
выката: тесты домена/API → проверка ответа без `tag` → проверка с `tag`.

## Open Questions

1. `active_tag` для неизвестного тега: пустая строка (принято в спеке) или эхо
   обрезанного запроса (текущий код). Решение меняет одно поле ответа и
   соответствующие тесты.
2. Нужно ли фиксировать `400` при повторном `tag` или достаточно брать одно
   значение. В спеке принят `400`.
3. Порядок `tags`: детерминированная сортировка (принято) или порядок первого
   появления в пуле.
4. Считать ли `tag` из одних пробелов пустым (принято) или неизвестным тегом.
