# Proposal: фильтр подборок по тегу (логика)

## Why

Теги уже хранятся в подборках и показываются на карточках, но API не умеет
отдавать подборки только с нужным тегом. Пользователю приходится просматривать
весь случайный список, хотя нужный набор уже есть в данных. Нужен серверный
фильтр по одному тегу, который не меняет избранное, корзину и схему БД.

## What Changes

- `GET /api/collections` принимает необязательный параметр `tag`.
- Пустой или отсутствующий `tag` сохраняет текущее поведение: случайная
  выборка всех активных подборок.
- Сравнение тега выполняется без учёта регистра; пробелы по краям
  отбрасываются.
- Неизвестный тег возвращает `200` и пустой `collections`.
- Тег длиннее 64 символов после обрезки возвращает `400`.
- В успешный ответ добавляются `tags` (все доступные теги активного пула) и
  `active_tag` (каноническое значение тега или пустая строка).
- Случайная выборка и лимит 12 применяются внутри отфильтрованного набора;
  если подходящих подборок меньше 12, возвращаются все.
- Избранное, корзина, существующие поля ответа и схема БД не меняются.
- UI (чипы, экраны, состояния) в границы этой спеки не входит.

## Capabilities

### New Capabilities

- `collections-tag-filter`: серверное поведение `GET /api/collections` при
  фильтрации активных подборок по одному тегу, включая список доступных
  тегов, каноническое значение и граничные случаи.

### Modified Capabilities

Нет: в `openspec/specs/` пока нет основных спек, чьи требования меняются.

## Impact

- HTTP API: `GET /api/collections` (новый необязательный query-параметр и два
  новых поля успешного ответа).
- Данные: активный пул подборок и их теги читаются как раньше; схема БД не
  меняется.
- Код: `internal/httpapi`, `internal/domain`, `internal/store`, тесты API и
  домена.
- Избранное и корзина: поведение и формат ответов не меняются.
- Новые зависимости и новые эндпоинты не добавляются.

## Non-Goals

- Чипы, экраны, состояния загрузки/пустоты/ошибки и доступность UI.
- Несколько тегов одновременно, поиск по тексту, сортировка, счётчики.
- Сохранение фильтра в URL или на сервере.
- Отдельный эндпоинт `/api/tags`.
- Изменение схемы БД, логики избранного и корзины.
- Изменение кодов и сообщений ошибок других эндпоинтов.

## Open Questions

1. **`active_tag` для неизвестного тега.** Задание требует «каноническое
   значение или пустая строка», а текущий код и `contract.md` отдают эхо
   обрезанного запроса. В этой спеке по умолчанию принята пустая строка;
   нужно подтвердить, оставляем ли эхо.
2. **Порядок `tags`.** Требование «все доступные теги» не задаёт порядок.
   По умолчанию принят детерминированный порядок по возрастанию кодовых
   точек; нужно подтвердить, что клиент не ожидает другого порядка.
3. **Несколько написаний одного тега в пуле.** Если «Ужин» и «ужин» есть в
   разных подборках, какое написание считать каноническим? По умолчанию
   принято лексикографически наименьшее после обрезки.
4. **Повторный параметр `tag`.** Задание не описывает `?tag=a&tag=b`.
   По умолчанию принят `400`; нужно подтвердить, что это не расширение сверх
   задачи.
5. **Пробельный `tag`.** Считать ли значение из одних пробелов пустым тегом
   (вернуть все подборки). По умолчанию принято «да».
